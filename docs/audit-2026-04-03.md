## C. Eight-Dimension Analysis

### 1. Architecture (Score: 4/5)

**Strengths:**
- Clean separation between clinical content (YAML flows in `flows/`) and UI (Vue components in `src/`). Domain experts can edit YAML without touching code. (`flows/strip.yaml`, `flows/bacteriurie.yaml`)
- Normalized Pinia store design with flat entity maps (questions, steps, results, resultsLogic) avoids deeply nested state. (`src/store/questionnaireStore.ts:40-44`)
- Build-time YAML compilation via decision-engine-core Vite plugin ensures no runtime YAML parsing; the browser only receives validated JSON. (`vite.config.js:4,21`)
- Role-based flow conditioning (`_role` injected into answer map) elegantly gates triage vs behandelaar paths without duplicating flows. (`src/store/questionnaireStore.ts:183-189`)

**Issues:**
- **SPEC-U01: decision-engine-core is an opaque tarball.** The engine (`decision-engine-core-1.0.0.tgz`) is not version-controlled source. The Vite plugin, condition validator, and outcome determiner are black boxes. If a clinical logic bug exists in the engine itself, it cannot be audited from this repo. Consider publishing to a private registry or including source. (`package.json:29`, `decision-engine-core-1.0.0.tgz`)
- **SPEC-U02: Leukocyturie follow-up routing is implicit.** The leukocyturie flow shows results like "Dipslide geindiceerd" or "Urinekweek geindiceerd" but does not use `redirect:` to actually navigate the user to the dipslide/kweek flow. The user must manually navigate back to the landing page and select the appropriate test. This breaks the clinical workflow continuity. (`flows/leukocyturie.yaml:100-116`)

### 2. Security (Score: 4/5)

**Strengths:**
- ESLint security plugin is actively enforced on all source files with explicit rule configuration. (`eslint.config.js:30-33`)
- Supabase anon key is injected via build-time env vars (GitHub secrets), not committed to repo. Admin routes are auth-gated. (`src/router/index.ts:91-99`, `CLAUDE.md:49-50`)
- Error handling strips internal details from user-facing messages, with Dutch-language fallbacks. Stack traces are only persisted to Supabase, never shown to users. (`src/lib/errors.ts:58-119`)
- External links use `rel="noopener noreferrer"` consistently. (`src/views/ResultPage.vue:189`)

**Issues:**
- **SPEC-U03: v-html used with marked output.** The QuestionnairePage renders markdown from YAML question descriptions via `v-html="compiledMarkdown(currentQuestion.description)"`. While the content is author-controlled (not user input), there is no DOMPurify sanitization layer. If a flow author accidentally includes a script tag or a malicious YAML edit occurs, XSS is possible. (`src/views/QuestionnairePage.vue:84-85`, `src/views/QuestionnairePage.vue:103`)
- **SPEC-U04: No Content Security Policy headers.** The netlify.toml lacks CSP headers. The inline theme-detection script in `index.html:9-12` would need a nonce or hash, but even a report-only CSP would improve the security posture. (`netlify.toml:1-11`, `index.html:9-12`)
- **SPEC-U05: npm audit shows 5 vulnerabilities.** While all appear to be in dev dependencies (brace-expansion, flatted, lodash, minimatch), the lodash and flatted issues are high-severity. Run `npm audit fix` to resolve.

### 3. Performance (Score: 5/5)

**Strengths:**
- Dual compression (Brotli + gzip) via vite-plugin-compression ensures minimal transfer sizes. (`vite.config.js:59-68`)
- Lazy-loaded routes for QuestionnairePage and admin views avoid loading clinical flow rendering code until needed. (`src/router/index.ts:21`, `src/router/index.ts:75-82`)
- CSS containment (`contain: layout style paint`) on scrollable content area prevents layout thrashing. (`src/App.vue:70`)

**Issues:**

### 4. Reliability (Score: 2/5)

**Strengths:**
- Build-time YAML validation catches structural errors before deployment. The decision-engine-core plugin validates all flows during `vite build`. (Console output: `[buildFlows] Successfully built...`)
- Error boundary with circuit breaker pattern in log-sink prevents cascading failures if Supabase is unreachable. (`src/lib/log-sink.ts:75-78`)

**Issues:**
- **SPEC-U06: Zero test files exist.** This is a clinical decision support application prescribing antibiotics with specific dosages, contraindications, and urgency levels. The complete absence of tests is the most critical finding in this audit. At minimum, the following must be tested:
  - Every YAML flow path produces the expected result key for given inputs
  - Redirect chains (strip -> bacteriurie) resolve correctly
  - Role-based conditioning (triagist sees triage results, behandelaar sees treatment)
  - Multi-select logic in gezonde-vrouwen (all 7 criteria required)
  - Contraindication display gating in ResultPage
  - Edge case: catheter question skipped for pregnant patients (`flows/bacteriurie.yaml:107-108`)
  (`vite.config.js:18-19`: `passWithNoTests: true`)
- **SPEC-U07: No runtime YAML/JSON schema validation.** The fetched main.json is trusted without schema validation at runtime. If the CDN serves a corrupted or outdated file, the app will silently malfunction. A JSON schema check on the fetched data would catch structural errors. (`src/store/questionnaireStore.ts:146-148`)
- **SPEC-U08: determineResult navigates to /error on null outcome without diagnostics.** When no logic rule matches the current answers, the user sees a generic error page with no indication of what went wrong clinically. This could mask a YAML logic gap where a valid clinical path has no matching rule. (`src/views/QuestionnairePage.vue:279-281`)

### 5. UX / Clinical Usability (Score: 4/5)

**Strengths:**
- Contraindication checklist gates treatment display -- the clinician must explicitly check each contraindication before seeing the prescribed treatment. This is a strong safety pattern. (`src/views/ResultPage.vue:88-126`)
- Copy-to-EPD documentation with single click supports real clinical workflow (paste into electronic patient dossier). (`src/views/ResultPage.vue:155-174`)
- Keyboard navigation with letter shortcuts (A, B, C...) for desktop users enables rapid questionnaire completion. (`src/views/QuestionnairePage.vue:326-340`)
- Touch-optimized targets (min-height 56px) and responsive layouts for mobile use during patient consultations. (`src/views/QuestionnairePage.vue:499`)
- Role toggle persisted in localStorage so triagists and behandelaars see appropriate content without re-selecting each session. (`src/store/roleStore.ts:8-9`)

**Issues:**
- **SPEC-U09: No breadcrumb or progress indicator during questionnaire.** In long flows like bacteriurie (up to 6 steps), the user has no sense of how many questions remain. A step indicator (e.g., "Stap 3 van 6") would reduce abandonment and improve orientation. (`src/views/QuestionnairePage.vue:1-107`)
- **SPEC-U10: Back button in ResultPage uses router.back().** If a user bookmarks or shares a result URL (e.g., `/info/uti.local.healthy.1`) and opens it directly, `router.back()` navigates to the browser's previous page (possibly another site entirely), not back to the questionnaire. (`src/views/ResultPage.vue:286-288`)

### 6. Code Quality (Score: 4/5)

**Strengths:**
- TypeScript strict mode enabled with consistent type annotations throughout. No `any` types visible in application code. (`tsconfig.json:8`: `"strict": true`)
- Structured logging system with 6 levels, module tagging, CSS-styled browser console output, and Supabase persistence. Professional-grade observability for a small app. (`src/lib/logger.ts:1-228`)

**Issues:**
- **SPEC-U11: Question type mismatch between YAML and TypeScript.** YAML flows use `type: select` and `type: multi_select`, but the TypeScript Question interface defines `type: 'single' | 'multiple' | 'multi_select'`. The decision-engine-core likely transforms `select` to `single` during compilation, but this transformation is opaque and the type union does not include `select`. (`src/types/index.ts:36`, `flows/strip.yaml:8`)
- **SPEC-U12: Popover state management uses mutable timeout refs.** The popover show/hide logic in QuestionnairePage uses a `let hidePopoverTimeout` with manual clearTimeout/setTimeout. This is fragile and could cause flickering on rapid mouse movements. A composable or debounce utility would be cleaner. (`src/views/QuestionnairePage.vue:133,396-401`)

**Strengths:**
- CLAUDE.md is comprehensive with all commands, conventions, and CI/CD documentation. (`CLAUDE.md:1-51`)
- Pre-commit hooks via husky + lint-staged run oxlint + eslint + format check on staged files. (`package.json:21-26`)

- **SPEC-U15: No local YAML validation script.** Developers must run a full `vite build` to check if YAML changes are valid. A standalone `validate-flows` script would speed up the feedback loop.

### 8. Future-proofing (Score: 3/5)

**Strengths:**
- YAML-based flow definitions make it straightforward to add new decision trees (e.g., SOA diagnostics, recidiverende UWI) without touching application code. The flow graph is fully data-driven.
- Guideline review dates are tracked in the About page with explicit per-guideline timestamps, supporting periodic evidence review. (`src/views/AboutPage.vue:74-100`)

**Issues:**
- **SPEC-U16: No versioned flow schema.** YAML flows have `version: '1'` but there is no schema evolution mechanism. If the flow format changes (e.g., adding `severity` to results, or `weight` to conditions), there is no migration path for existing flows. A JSON Schema definition for the flow format would enable automated validation and versioned migrations.
- **SPEC-U17: Bacteriurie flow is 1,225 lines and growing.** The largest flow handles 8 patient groups x 2 invasion types x catheter status x multiple treatments, resulting in ~80 logic rules. This monolithic YAML will become increasingly difficult to maintain. Consider splitting into sub-flows (e.g., `bacteriurie-local.yaml`, `bacteriurie-tissue-invasion.yaml`) or introducing a composition mechanism.
- **SPEC-U18: No i18n infrastructure.** All UI text and clinical content is hardcoded in Dutch. While the primary audience is Dutch-speaking, AZC (asylum seeker center) contexts may benefit from multilingual support. The current architecture has no extraction or translation mechanism.

## G. Clinical Flow Correctness Review

### strip.yaml
- Logic is complete: nitriet+/- x leuko+/- x ery+/- covers all 4 terminal states (redirect bacteriurie, redirect leukocyturie, redirect hematurie, show noConclusiveAbnormality).
- Erytrocyten test only shown when both nitriet and leuko are negative (correct per NHG).
- Leukocyten options include +, ++, +++ which all map to `positive` -- correct, as the clinical threshold is any positive.

### bacteriurie.yaml
- Triage rules are ordered first (lines 1064-1092), ensuring triagists are redirected before treatment questions are evaluated. This is correct.
- Pregnant + tissue invasion correctly redirects to gynaecoloog (line 1097-1098).
- Elderly asymptomatic correctly gets "no antibiotics" result (line 1101).
- Catheter patients without tissue invasion correctly get "no treatment needed" (lines 1105-1112).
- Treatment options per population group match NHG-Standaard recommendations (nitrofurantoine 1e keuze for local, ciprofloxacine 1e keuze for tissue invasion).
- Elderly symptomatic female uses `treatmentLocalElderlyVulnerable` options mapping to `uti.local.vulnerable.*` results -- this is clinically appropriate (same treatment as vulnerable population).
- Elderly symptomatic male uses `treatmentLocalElderlyMen` mapping to `uti.local.men.*` -- correct (7-day nitrofurantoine vs 5-day for healthy).
- **Observation:** The catheter question conditions (`riskAssessment != elderly` AND `riskAssessment != pregnant`) at line 107-108 correctly skip the catheter question for elderly (who have their own sub-flow) and pregnant patients (for whom catheter management differs). However, the `!=` conditions use AND semantics (both must be true), which means the catheter question is shown for all other groups. This is correct behavior.

### gezonde-vrouwen.yaml
- All 7 criteria must be met (includes checks for each criterion). If any single criterion is not met, `other.ruleNotApplicable` is shown. The 7 individual `not_includes` checks at lines 143-156 correctly implement early termination.
- Treatment options include afwachtend beleid as option 0 (conservative), which is clinically appropriate per NHG guidance.
- The 20% misdiagnosis risk is appropriately documented in the question description (line 11).

### hematurie.yaml
- Proteinuria result correctly instructs blood pressure measurement + creatinine/eGFR + urine sediment with dysmorph erythrocyte count. This matches H&W guidance.
- Microscopic hematuria correctly recommends 1-week recheck with pre-test instructions (no exercise, avoid menstruation period).

### leukocyturie.yaml
- CAD patients correctly get "no treatment needed" (line 120-121).
- Asymptomatic elderly correctly get "no culture, active monitoring" (line 122-123).
- Symptomatic elderly correctly get "urine culture indicated" (line 124-125).
- Children only get dipslide or urinekweek options (no sediment), which differs from the general population options (dipslide, sediment, or culture). This distinction is clinically appropriate.

### dipslide.yaml / kweek.yaml / sediment.yaml
- MacConkey positive immediately redirects to bacteriurie (correct -- gramnegatieve groei is diagnostic).
- CLED threshold at 10^4 KVE/ml matches NHG guidance.
- Kweek threshold at 10^5 KVE/ml is standard. The ambiguous option (low growth + clinical suspicion) correctly recommends microbiology consultation.
- Sediment contamination (plaveiselepitheel) correctly triggers re-test instruction.

**No clinical logic errors were identified in any of the 8 flows.**
