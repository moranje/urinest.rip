## C. Dimension Analysis

### 1. Architecture (4/5)

**Strengths:**
- Clean three-layer separation: YAML flows (clinical content) -> decision-engine-core Vite plugin (build-time compilation) -> Vue components (presentation). This architecture means clinical content authors can update YAML without touching application code.
- Normalized Pinia store (`questionnaireStore.ts`) with flat lookup maps for O(1) access to questions, steps, results, and logic rules. The 241-line store is well-structured.
- Role-based condition injection (`_role`) at the flow level cleanly separates triage vs. behandelaar pathways without branching in UI code.
- Cross-flow redirects work elegantly: strip -> bacteriurie/leukocyturie/hematurie, dipslide -> bacteriurie, sediment -> bacteriurie, kweek -> bacteriurie. The redirect/show outcome pattern is effective.
- Well-structured error handling pipeline: `errors.ts` (classification + Dutch user messages) -> `logger.ts` (6-level structured output with CSS console styling) -> `log-sink.ts` (batched persistence with circuit breaker) -> Supabase.
- Error context collection (`error-context.ts`) with browser/OS parsing, source location extraction, session IDs, and FNV-1a fingerprinting for error grouping is production-grade.

**Weaknesses:**
- `decision-engine-core` is a local tarball (`decision-engine-core-1.0.0.tgz`), not a versioned npm package. This makes updates opaque and reproducibility fragile.
- The questionnaire page at 727 lines (including 300+ lines of CSS) is the largest single component. The logic, popover management, and keyboard handling could be extracted.
- Stale `.nuxt/` directory from a previous Nuxt-based architecture remains in the project root, adding confusion.

### 2. Security (3/5)

**Strengths:**
- `.env` is properly gitignored and not tracked (verified by `git ls-files`). `.env.example` documents the expected variables without secrets.
- CI pipeline includes both secret scanning (regex for JWTs in source) and `.env` tracking verification.
- eslint-plugin-security is enabled with reasonable rule configuration.
- Supabase client (`client.ts`) gracefully degrades to null when env vars are missing -- no crashes, no key exposure.
- v-html usage (`compiledMarkdown`) operates on trusted content from own YAML data, not user input. Documented in eslint config.

**Weaknesses:**
- npm audit has not been remediated since the previous audit flagged vulnerabilities.
- The `.env` file has permissions `0644` (world-readable). Should be `0600`.
- No Content-Security-Policy headers configured in `netlify.toml` (only contains SPA redirect rules).
- The admin dashboard (`/admin/logs`, `/admin/login`) uses Supabase auth with email/password. No MFA support, no rate limiting at the application layer (relies on Supabase built-in).
- Source maps are uploaded to Supabase Storage, but no access control verification is documented for the `sourcemaps` bucket.

### 3. Performance (4/5)

**Strengths:**
- Brotli + gzip compression configured via `vite-plugin-compression` with 1024-byte threshold.
- PWA with offline support: `workbox` configured with navigateFallback and comprehensive glob patterns.
- Lazy loading for non-critical routes: `QuestionnairePage.vue`, `AdminLogin.vue`, `LogDashboard.vue` are dynamically imported.
- `main.json` is fetched with cache-busting query parameter (`?t=Date.now()`), preventing stale clinical data.
- CSS containment used strategically (`contain: layout style paint` on `.app-content` and `.result-main`).
- Skeleton loading states for both questionnaire and result pages.
- Animation durations use CSS custom properties for consistent timing.

**Weaknesses:**
- No resource hints (preconnect to Supabase domain) in `index.html`.
- All 8 YAML flows compile into a single `main.json` -- no code splitting for individual flows. For 8 small flows this is fine, but will not scale.
- No image optimization pipeline (SVG components are inline, which is good, but no `<link rel="preload">` for the icons referenced in the PWA manifest).

### 4. Reliability / Clinical Correctness (3/5)

**This is the most critical dimension for a medical decision aid.**

**Strengths -- Clinical Content:**
- Antibiotics are correctly ordered per NHG-Standaard: nitrofurantoine (1st), fosfomycine (2nd), trimethoprim (3rd) for uncomplicated cystitis; ciprofloxacine (1st), amoxicilline/clavulaanzuur (2nd), cotrimoxazol (3rd) for tissue invasion.
- Contraindications are present for every antibiotic: eGFR thresholds, G6PD, pregnancy/breastfeeding, cumarine/methotrexaat interactions, neuropathy for fluoroquinolones.
- Dosages match NHG-Standaard: nitrofurantoine 2dd 100mg mga or 4dd 50mg (5 days), fosfomycine 3g single dose, ciprofloxacine 2dd 500mg, etc.
- Special populations handled: pregnant (gynaecologist referral for pyelonephritis, no ciprofloxacine), children (amoxicilline/clavulaanzuur with weight-based dosing, echo for <2yr), elderly (Verenso criteria for symptomatic vs asymptomatic), catheter patients (katheter wisselen before antibiotics).
- Triage role correctly blocks treatment selection and provides urgency codes (U2 for tissue invasion, U3 for vulnerable populations).
- `gezonde-vrouwen.yaml` correctly implements all 7 NHG criteria for clinical diagnosis without urinalysis, including the 20% false-positive risk disclosure.
- Strip flow correctly implements the nitriet -> leukocyten -> erytrocyten cascade with appropriate redirects.
- Documentation fields (`documentation`) provide copy-paste-ready text for the EPD (electronic patient record).

**Strengths -- Safety Mechanisms:**
- Contraindications checklist on ResultPage blocks treatment display until all items are explicitly checked. This is a good forcing function.
- Warning sections (eGFR dose adjustments, fluoroquinolone aorta risk) are visually prominent with colored banners.
- Cross-flow redirects ensure a positive finding always leads to the appropriate specialist flow (e.g., positive dipslide -> bacteriurie).

**Weaknesses -- Clinical:**
- **Zero automated tests.** This is a clinical tool that prescribes antibiotics, and there are no tests verifying that any clinical path produces the correct outcome. A regression in the YAML or engine could silently change treatment recommendations. This remains the single most critical issue.
- Guideline review dates are 6+ weeks old (Feb 21-22, 2026). The CLAUDE.md convention states review dates must be updated with content changes, but no automated check enforces this.
- The `bacteriurie.yaml` flow (1,225 lines) has approximately 80 logic rules. Manual verification of all condition combinations is impractical without automated testing.
- `treatmentTiCadWoman` conditions include `riskAssessment == healthy` -- this maps "healthy + catheter" to a "catheter woman" treatment. The naming is confusing: a patient with a catheter who answers "Nee" (healthy) at risk assessment gets CAD woman treatment. This works because the flow assumes healthy + catheter = woman, but this implicit assumption is not documented.
- The `passWithNoTests: true` Vitest config actively suppresses the "no tests" signal, masking the problem.

**Weaknesses -- Structural:**
- No schema validation of YAML flows beyond what `decision-engine-core` does at build time. There is no way to verify that all logic paths are reachable or that all result keys referenced in logic actually exist as defined results.
- No dead-code detection for unreferenced result definitions.
- No flow version tracking beyond the static `version: '1'` field -- all flows are at version 1 despite content changes.

### 5. UX (4/5)

**Strengths:**
- Material Design 3 design system with proper design tokens (tokens.css, themes.css), dark mode support via system preference, and consistent component styling.
- Keyboard navigation: options selectable via A/B/C keys on non-touch devices, with visual prefixes.
- Smooth transitions between questions (translateY animations) and staggered result section entrance.
- Info popovers with viewport-aware positioning (checks space above/below, clamps to margins).
- Treatment section hidden behind contraindication checklist creates a deliberate workflow (check first, then see treatment).
- Copy-to-clipboard for EPD documentation with toast feedback.
- Role toggle (behandelaar/triagist) persisted in localStorage.
- PWA prompt-based updates (not auto-update) -- correct for a clinical tool where unexpected behavior changes would be dangerous.
- Back navigation with question history stack.
- Touch targets meet 44px minimum (`--min-touch-target`).

**Weaknesses:**
- No breadcrumb or progress indicator during the questionnaire flow. Users cannot see how many steps remain.
- The landing page grid shows 5 test types + 3 UTI flows with no visual hierarchy guidance for "where do I start?" -- a new user may not know that strip is the typical first step.
- Error page (`ErrorPage.vue`) is minimal (36 lines). No suggested recovery actions.
- No confirmation dialog when navigating away from a partially-completed questionnaire (answers are cleared on re-entry).

### 6. Code Quality (4/5)

**Strengths:**
- TypeScript throughout with strict types for all domain entities (`types/index.ts` -- 135 lines covering the full domain model).
- Zero lint warnings across both oxlint (95 rules) and eslint (with security plugin).
- Clean type-check pass with vue-tsc.
- Conventional commits enforced via commitlint + husky hooks.
- Consistent naming: Dutch for clinical content (YAML, user-facing text), English for code.
- Error handling is comprehensive: global Vue errorHandler, unhandledrejection listener, Dutch error classification, circuit-breaker on log persistence.
- Logger implementation (`logger.ts`, 227 lines) is well-designed: module-scoped loggers, configurable levels, CSS-styled console output, sink system, runtime override via `window.__setLogLevel`.

**Weaknesses:**
- Stale `.nuxt/` directory with 25+ generated TypeScript files from a previous architecture.
- `QuestionnairePage.vue` at 727 lines mixes too many concerns: question navigation, popover management, keyboard shortcuts, markdown compilation, and 300 lines of CSS.
- Some `console.error` calls in `questionnaireStore.ts` and `QuestionnairePage.vue` bypass the structured logger.
- The `compiledMarkdown` function calls `marked.parse()` synchronously on every render without memoization.

### 7. Developer Experience (3/5)

**Strengths:**
- `CLAUDE.md` documents all commands, conventions, CI/CD, and architectural decisions.
- `npm run dev` provides instant local development with Vite HMR.
- lint-staged + husky ensures quality gates on every commit.
- Parallel CI (lint + type-check + test run simultaneously).
- `.env.example` documents expected environment variables.

**Weaknesses:**
- Zero test files. `vitest` is configured but `passWithNoTests: true` means the test step always passes. Developers get no feedback on regressions.
- `decision-engine-core` is an opaque tarball. No source code, no documentation of the YAML schema, no way to debug compilation issues beyond error messages.
- No Storybook or visual testing for the 12 components.
- No E2E testing (no Playwright/Cypress). For a clinical tool, happy-path E2E tests would be high-value.
- CI runs on `master` branch, but the local repo's default branch is `main`. This mismatch means CI never triggers on local pushes.

### 8. Future-proofing (3/5)

**Strengths:**
- YAML-first architecture makes adding new flows straightforward (add YAML file, it appears in the build).
- Role system is extensible (new roles can be added by extending `UserRole` type and adding conditions in YAML).
- Supabase logging infrastructure is ready for analytics/audit trails.
- PWA with offline support makes the app resilient for use in settings with poor connectivity.

**Weaknesses:**
- All flows compile to a single `main.json`. Adding many flows will increase load time for all users.
- No i18n infrastructure. The app is Dutch-only. Adding English would require duplicating all YAML content.
- No versioning strategy for flows beyond the static `version: '1'`. Cannot track which version of clinical content a user saw.
- No audit trail of which clinical decisions were made (only errors are logged, not successful completions).
- The `decision-engine-core` dependency is a single point of risk. If the tarball becomes incompatible with future Vite versions, there is no fallback.

## D. Clinical Flow Audit

### D.1 Strip Flow (strip.yaml)

**Path analysis:**
1. Nitriet+ -> redirect to bacteriurie (correct: positive nitrite = bacteriuria)
2. Nitriet-, Leuko+ -> redirect to leukocyturie (correct: isolated leukocyturia)
3. Nitriet-, Leuko-, Ery+ -> redirect to hematurie (correct: isolated erythrocyturia)
4. Nitriet-, Leuko-, Ery- -> "Geen afwijkingen gevonden" (correct)

**Assessment:** All paths clinically correct per NHG-Standaard. The cascade correctly prioritizes nitriet > leukocyten > erytrocyten. Leukocyten and erytrocyten questions correctly appear conditionally (only when prior tests are negative).

### D.2 Gezonde Vrouwen Flow (gezonde-vrouwen.yaml)

**Path analysis:**
- All 7 criteria must be checked for the healthy-woman rule to apply. If any criterion is not met, the flow shows "Diagnose niet mogelijk op anamnese alleen."
- When all criteria met: choice between afwachtend beleid, nitrofurantoine, fosfomycine, trimethoprim.

**Assessment:** Matches NHG-Standaard section "Evaluatie". The 7 criteria correctly include: prior proven UTI, dysuria as main complaint, no tissue invasion signs, <1 week duration, no STI risk, no vaginal irritation, patient self-diagnosis. The 20% false-positive risk is disclosed in the description.

### D.3 Bacteriurie Flow (bacteriurie.yaml)

**Path analysis (selection of critical paths):**
- Tissue invasion + pregnant -> gynaecologist referral (correct per NHG + NVOG)
- Tissue invasion + triagist -> U2 urgent referral (correct per NHG-TriageWijzer)
- Local + elderly + asymptomatic -> no treatment (correct per Verenso: no treatment of asymptomatic bacteriuria)
- Local + catheter -> no treatment in absence of tissue invasion (correct per NHG)
- Tissue invasion + catheter -> katheter wisselen + kweek + antibiotica (correct per Verenso)

**Dosing spot-checks:**
- Nitrofurantoine cystitis: 5d 2dd 100mg mga or 4dd 50mg -- **correct**
- Nitrofurantoine elderly cystitis: mentions "NHG: 7 dagen, Verenso: 5 dagen" -- **correct** (NHG recommends 7 days for elderly, Verenso 5 days for frail elderly)
- Ciprofloxacine pyelonephritis: 7d 2dd 500mg (women), 14d 2dd 500mg (men) -- **correct** (men get longer course due to prostatitis consideration)
- Amoxicilline/clavulaanzuur children: 10d, <40kg: 50/12.5 mg/kg/dag in 3 doses -- **correct**
- Fosfomycine: eenmalig 3g (<50kg: 2g) -- **correct**

**Concern:** The catheter question (`urinaryCatheter`) has conditions `riskAssessment != elderly` and `riskAssessment != pregnant`. This means elderly patients and pregnant patients are never asked about catheters. For pregnant patients this is reasonable (catheter UTI in pregnancy should go to gynaecologist regardless). For elderly patients, the flow goes through the `elderly` symptomatic/asymptomatic question instead. However, an elderly patient WITH a catheter AND tissue invasion would follow the elderly TI pathway, not the catheter TI pathway. The treatment is the same (ciprofloxacine first-line) but the documentation does not mention "katheter wisselen" for elderly catheter patients in the TI pathway. This could be a clinical safety gap.

### D.4 Leukocyturie Flow (leukocyturie.yaml)

**Assessment:** Correctly differentiates CAD patients (no treatment), asymptomatic elderly (no culture needed), symptomatic elderly (culture), children (dipslide or culture), and general population (dipslide, sediment, or culture). Matches NHG-Standaard and Verenso.

### D.5 Hematurie Flow (hematurie.yaml)

**Assessment:** Correctly categorizes visible hematuria (alarmsymptoom -> spreekuur), proteinuria (nefrologische analyse + lab), and microscopic hematuria (herhaling na 1 week). Sources include NVU and NVKC guidelines. The proteinuria documentation correctly specifies the full workup (creatinine/eGFR, glucose, sediment with dysmorfe erytrocyten, ACR).

## E. SPECs

### SPEC-U001: Clinical Path Testing

**Priority:** CRITICAL
**Effort:** L (3-5 days)
**Rationale:** A clinical decision aid prescribing antibiotics with zero automated tests is a patient safety risk. Any regression in YAML, engine, or condition evaluation could silently produce wrong treatment recommendations.

**Acceptance criteria:**
1. Create test fixtures that load `main.json` and exercise the decision engine directly (no DOM needed).
2. Test every terminal result in every flow is reachable (100% result coverage).
3. Test every redirect produces a valid questionnaire ID.
4. Test specific critical clinical paths:
   - Strip nitriet+ -> bacteriurie redirect
   - Gezonde vrouwen: all 7 criteria met -> each treatment option
   - Gezonde vrouwen: 1 criterion missing -> ruleNotApplicable
   - Bacteriurie: pregnant + tissue invasion -> gynaecologist referral
   - Bacteriurie: triagist + tissue invasion -> U2
   - Bacteriurie: elderly + asymptomatic -> no treatment
   - Bacteriurie: catheter + local -> no treatment
   - Leukocyturie: CAD -> no treatment
5. Test that role=triagist blocks all treatment selection questions (all treatment questions have `_role != triagist` condition).
6. CI fails on test failure. Remove `passWithNoTests: true` from vitest config.

### SPEC-U002: CI Branch Mismatch Fix

**Priority:** HIGH
**Effort:** XS (15 min)
**Rationale:** CI workflow triggers on `master` but local default branch is `main`. CI never runs.

**Acceptance criteria:**
1. Update `.github/workflows/ci.yml` to trigger on `main` instead of `master`, or rename the local branch.
2. Verify CI runs on next push.

### SPEC-U003: Content-Security-Policy Headers

**Priority:** HIGH
**Effort:** S (1 hour)
**Rationale:** Clinical tool with no CSP headers. A reflected XSS could inject false medical advice.

**Acceptance criteria:**
1. Add `_headers` file or update `netlify.toml` with CSP headers.
2. Allow: self, Supabase domain, inline styles (Vue requires them).
3. Block: eval, inline scripts, external frame embedding.
4. Test that the app still works with CSP enabled.

### SPEC-U004: Elderly Catheter TI Documentation Gap

**Priority:** HIGH
**Effort:** S (1-2 hours)
**Rationale:** Elderly patients with a catheter AND tissue invasion follow the elderly TI pathway, but the result documentation does not mention "katheter wisselen" (catheter replacement before antibiotics). This is a clinical safety gap -- the Verenso richtlijn explicitly recommends replacing the catheter before starting antibiotics.

**Acceptance criteria:**
1. Add a separate `sexTissueInvasionCatheter` question for elderly TI patients, or add catheter-specific results/documentation for elderly TI paths.
2. Alternatively, add the catheter question for elderly patients when tissue invasion is present, and route to the existing catheter TI results.
3. Verify the documentation text mentions "verblijfskatheter wisselen" when applicable.

### SPEC-U005: Flow Version Tracking

**Priority:** MEDIUM
**Effort:** S (2 hours)
**Rationale:** All flows are at `version: '1'` despite multiple content revisions. There is no way to determine which version of clinical content a user consulted.

**Acceptance criteria:**
1. Bump flow versions when content changes (semver or incrementing integer).
2. Display the flow version on the result page.
3. Include the flow version in the Supabase log entry for audit trail.
4. Add a CI check that flow version is bumped when flow content changes.

### SPEC-U006: Remove Stale .nuxt Directory

**Priority:** LOW
**Effort:** XS (5 min)
**Rationale:** Leftover `.nuxt/` directory from the previous architecture adds 25+ generated TypeScript files that confuse IDE indexing and git status.

**Acceptance criteria:**
1. Delete `.nuxt/` directory.
2. Add `.nuxt` to `.gitignore` if not already present (it is present).

### SPEC-U007: QuestionnairePage Decomposition

**Priority:** LOW
**Effort:** M (1-2 days)
**Rationale:** At 727 lines the questionnaire page mixes navigation logic, popover management, keyboard handling, markdown compilation, and extensive CSS.

**Acceptance criteria:**
1. Extract popover logic into a `usePopover` composable.
2. Extract keyboard navigation into a `useKeyboardNav` composable.
3. Memoize `compiledMarkdown` calls (or move to a computed map).
4. Target: QuestionnairePage.vue under 300 lines.

### SPEC-U008: Guideline Review Date Automation

**Priority:** MEDIUM
**Effort:** S (2 hours)
**Rationale:** Guideline review dates in `AboutPage.vue` must be manually updated. No automated check enforces this convention documented in CLAUDE.md.

**Acceptance criteria:**
1. Add a CI check that warns when a flow file has been modified more recently than the corresponding guideline review date in `AboutPage.vue`.
2. Alternatively, add `reviewed` metadata to each YAML flow file and display it from there (single source of truth).

## G. Positive Highlights

1. **Clinical content quality is high.** Dosages, contraindications, treatment hierarchies, and patient-group differentiations match current NHG-Standaard and Verenso guidelines. The amount of clinical detail in the YAML flows (including EPD documentation text, explainer text, and source links) is impressive for a small tool.

2. **Error handling is production-grade.** The error classification -> structured logging -> batched persistence -> Supabase pipeline with circuit breaker, session IDs, FNV-1a fingerprinting, and source location extraction would not be out of place in a much larger application.

3. **The contraindication checklist pattern is a genuine safety feature.** Hiding treatment behind explicit contraindication verification is a UX decision that prioritizes safety over speed. This is the right tradeoff for a prescribing tool.

4. **The role system is well-designed.** The triagist role correctly blocks all treatment questions at the YAML level (via `_role != triagist` conditions) and provides appropriate urgency-coded referral results. This means the same flow YAML serves both roles without code duplication.

5. **The YAML-first architecture pays dividends.** A clinician could review and update the treatment recommendations in plain YAML without needing to understand Vue, TypeScript, or the build system.
